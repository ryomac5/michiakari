# 関西の鉄道の運転見合わせ事例の調査

調査日は 2026-11-04 と 2026-11-05 である。目的は、実績から運転再開までの残り時間を推定し検証できる形で記録することである。2024 年以降に絞り、時間付きの58件を記録した（従来51件、JR西日本3件、叡山電鉄4件）。別に、時刻不足・関西外などの分類用補助11件も記録した。件数が少ないため、以下の分析は傾向の仮説にとどめる。

再現可能な集計と現在のcoreの予測値との比較は [検証報告書](validation_report.md) にある。[分類・バリエーションの一覧](classification_report.md) では69事例を8大分類・27種類に整理した。収集済み資料は運用の予測パラメータへ自動反映していない。

## 対象期間の扱い

対象は 2024-01-01 以降で、所要時間が出典から求まる事例である。初回の調査にあった 2022 年と 2023 年の 2 件は、消さずに cases_out_of_scope.jsonl に移した。京阪の 2024-11-26 三条の事例は、開始と再開の時刻が出典に無く所要時間が出せないため、同じファイルに移した。JR神戸線の 2026-06-29 舞子の事例は、40 分が停車した 1 本の時間であり線路の見合わせ時間ではないため、同じファイルに移した。

## 調べ方

WebSearch と WebFetch で個別のページを手で開いた。呼び出し回数は初回の約 95 回に加え、拡大で約 300 回である。X と非公式 API と運行情報ページの機械的な巡回は使わなかった。

手順は次のとおりである。事業者名と事象名と年で検索し、候補の事例を集めた。候補ごとに一次資料か新聞記事を開き、時刻と区間と原因を読んだ。事実だけを自分の言葉で書き、出典 URL を項目ごとに結びつけた。開けなかったページの内容は項目に入れず、notes に未確認と書いた。

拡大では、情報源ごとに担当を分けて集めた。京都新聞デジタルの人身事故、京都新聞デジタルの自然災害と設備、神戸新聞 NEXT、事業者のニュースリリース、その他の公開記事の 5 担当である。1 件の事例は 1 担当が記録し、重複は id と日付と路線で除いた。

時刻の扱いは次のとおりである。ごろや過ぎの付く時刻は approx を true にした。見合わせの開始が記事に無い事例は、事故や異常の発生時刻で代用し、approx を true にして notes に書いた。所要時間は開始と再開が両方そろう事例だけ機械で計算した。阪神の強風の事例だけは、記事が約 10 分と明記した値をそのまま記した。

機械での確認は次の 2 点を行った。cases.jsonl の全行が JSON として読めること。全行に出典 URL と所要時間があること。

## 分かったこと

集計と現在のcoreによる比較は [検証報告書](validation_report.md) を参照する。現在の人身事故モデルは、発生直後の比較でp50が60分に対し実績17件の中央値が100分だった。事例は報道や事後報告に偏るため、この差だけを根拠に運用パラメータを置き換えない。途中の段階の継続時間や実際に乗れた時刻は、この資料からは検証できない。

## 偏りと限界

報道に残るのは長い事例と影響人数の多い事例に偏る。短い事例も載るが、残りにくい。見合わせの開始が記事に無い事例は除いたため、開始が書かれやすい長い事例に寄った可能性がある。

情報源は京都新聞デジタルが 24 件、神戸新聞 NEXT が 11 件で、他社の件数は少ない。京都と兵庫の事例に偏り、大阪と和歌山の事例は少ない。JR西日本の湖西線の強風が 6 件のうち 4 件を占める。

再開時刻は上限値のものが多い。記事の時点で再開済みという書き方が多く、実際の再開はそれより前の可能性がある。部分再開があった事例は、全区間の再開を再開時刻にした。途中で一度再開した事例は、最初の開始から最後の再開までを所要時間にして notes に書いた。

道具の制約もある。大手の新聞社と放送局のサイトには到達できなかった。会員限定の記事と古い記事は 404 で開けなかった。アーカイブサイトは使えなかった。

人身事故では、当事者の年齢や性別や経緯を一切記録していない。路線と区間と時刻と分類だけを取った。

## 再生成と検査

このディレクトリで実行する。Node.jsとリポジトリのpnpm依存も必要。

```sh
uv sync --locked
uv run research.py
uv run classify_cases.py
uv run python -m unittest discover -s tests -v
```

個別の入口もuv run build_csv.py、uv run summarize_durations.py、uv run compare_with_dev_knowledge.pyで動く。比較は段階ごとのp50/p80の単純加算から、coreの実際の分布・分岐・下限の計算に置き換えた。

追加時はJSONLに日付・区間・原因・出典・閲覧日・概数と代用の注記を書く。原文や人物の情報は記録しない。開始と再開の組が不明、または単一列車の遅延のみなら集計対象に加えず、理由をscreened_candidates.jsonlに残す。

## 今回の分類拡充

叡山電鉄の安全報告書2025から、雨の弱まり後の再開2件、落雷で信号設備が故障した1件、雪・凍結でポイントが動かなかった1件を時間付き事例に追加した。動物接触後の車両損傷と救援、翌朝まで続く信号不具合、踏切内の自動車撤去も分類用に記録した。多摩都市モノレールの公表資料からは急病人、旅客トラブル、線路内立ち入り、降雪時の減速、大雨による設備損傷、落雷による構造物損傷、ポイント不良を追加した。京都駅の不審物確認も、再開時刻の分布には使わず分類用に記録した。

補助事例を関西の時間分布へ足さず、学習・検証済みのモデルと分類の網羅性を混同しない。利用者が放送から分かる原因と、事後に確定した故障原因も区別する。

## 所要時間の統計値

cases.jsonl と追加 2 ファイルの 141 件を、日付と路線と原因で重複を除いて合わせ、大分類と種類ごとに件数、最短、中央値、p80、最長を出す。補助事例は含めない。
件数 5 未満の種類は大分類の値に頼る印を付け、件数 3 未満の大分類にも印を付ける。報道に残る事例は長引いたものに偏る。
時間帯は止まった時刻で「平日の通勤時間帯」と「それ以外」に分ける。通勤時間帯は平日の 7〜9 時台と 17〜19 時台で、仮の値であり開発者に確かめる。祝日は区別せず、止まった時刻の無い 1 件は時間帯に数えない。
区分の件数が 5 未満なら、まぜた値を使う印を付け、p50 と p80 に全体の値を入れる。区分だけの値は ownP50 と ownP80 に残す。
`python3 -I build_incident_durations.py` で packages/core/params/incident-durations.ts を作り直す。手では書き換えない。

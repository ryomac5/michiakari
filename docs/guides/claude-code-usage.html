1. 要約

開発者が仕事をしている昼間に、Claude Code が並列の作業ツリーで実装を進めた。 開発者は夜に差分を確かめ、規則表の値に答え、シナリオを書き、翌日の目標を決めた。

この分業を成り立たせたのは 3 つの仕組みである。 守りの仕組みは、エージェントが触ってはいけない領域をフックと guard で遮断する。 委譲の仕組みは、根のセッションが計画と判断だけを担い、実装を子に振る。 記録の仕組みは、各ターンの終わりに作業記録を残し、次のセッションが引き継ぐ。

開発者本人が担ったのは、規則表に落とす知見の答え、シナリオ、判断結果の確認、動画のナレーションである。 それ以外のコード、文書、テスト、録画の台本は Claude Code が書いた。

2. 守りの仕組み

このアプリの価値は、元指令員の経験を落とした規則にある。 シナリオを機械に書かせては、作品の根拠が失われる。 知見の材料が公開のリポジトリに漏れても、根拠が損なわれる。

そこで守る対象を 2 つに定めた。 scenarios/ は開発者本人だけが書く領域である。 知見の材料はリポジトリ外のフォルダで管理し、コミットしない。 この 2 つを 4 層で守った。

フック

.claude/settings.json に PreToolUse のフックを 1 つ置いた。 Write、Edit、MultiEdit の前に protect-paths.mjs が走る。 対象のパスが保護ディレクトリなら exit 2 で止め、理由を伝える。 保護ディレクトリは scenarios/ と、知見の材料のフォルダである。 材料のフォルダは書き込みを止め、読むことだけを許す。

scenarios/foo.yaml は開発者本人が書く領域のため変更できません。
問題があれば docs/progress.md の「開発者に確認したいこと」に書いてください。

エージェントが内容に疑問を持ったときの出口は、作業記録への記入である。 この一文があるので、エージェントは止められても次の行動に迷わない。 開発者が自分で編集するときは ALLOW_PROTECTED_EDIT=1 を付けて起動する。

guard

フックは Claude Code のツール呼び出しだけを見る。 Bash 経由の書き込みやシンボリックリンクはすり抜ける。 その穴を pnpm guard が塞ぐ。

検査内容
承認記録scenarios/ の内容を承認記録のハッシュと照合する。未承認の差分があれば失敗する。
シンボリックリンクscenarios/ 内にリンクがあれば失敗する。
ブランチ差分main からの差分に scenarios/ の変更があれば失敗する。
内容検証pnpm validate で YAML と雛形の整合を確かめる。
材料の照合PRIVATE_NOTES_DIR の材料の文を、追跡中のファイルと照合する。文が写っていれば失敗する。

承認記録を書くのは pnpm guard:approve だけである。 このコマンドは /dev/tty から y の入力を要求する。 エージェントは TTY を持たないので、承認を代行できない。 pnpm guard はすべての自律作業の証明コマンドに含め、コミット前にも走らせた。

決定論モード

判断エージェントは claude と deterministic の 2 モードを持つ。 API キーが無ければ決定論モードで動き、文字列照合と規則で判断する。 数値計算は packages/core に置き、どちらのモードでも Claude に計算させない。

この設計は 2 つの効果を生んだ。 子エージェントのサンドボックスは API キーを持たないが、画面から録画まで通しで動かせる。 テストは乱れなく再現し、プロンプトの変更が計算を壊したかを切り分けられる。

e2e

シナリオの期待値から Playwright の振る舞いテストを生成した。 観測を 1 つ進めるたびに、結論と分岐点が期待どおりに変わることを確かめる。 地図のタイルとフォントは固定データに差し替え、外部に依存しない。

判断ロジック、プロンプト、ツールを変えたら e2e を流す規則にした。 開発者の答えを規則に落とした結果を、機械が毎回確かめる。

3. 委譲の仕組み

根のセッションは対話、要件整理、計画、委譲、判断、報告だけを担う。 実装は子に振る。 高性能なモデルを根に置く理由は、子への指示の質が結果を決めるからである。

委譲の契約

委譲文には 4 つを必ず書いた。 受け入れ条件は pnpm typecheck のような機械で判定できるコマンドにする。 触ってよいファイルを scope として限定する。 制約と禁止事項は要点のあとに書く。 子は会話履歴を見ないので、委譲文は自己完結にする。

子の報告を受けたら、根は受け入れ条件に照らして評価する。 子が完了と書いても根拠にはしない。 往復は 3 回を上限とし、収束しなければ分解のしかたを見直す。

レビューのモデル

実装とレビューは別系統のモデルにした。 同じ系統でレビューすると、盲点が共有されたままになる。 重要な差分のレビューには、そのとき使える最上位のモデルを指定した。

開発者の方針

実装は Claude の子に振る。 レビューは別系統の Codex に回し、同じ系統で見落としを共有しない。 このハッカソンが Claude で作ることを競うので、実装を Codex には任せない。

11-05 の運用で分かったこと

11-05 のタスクグラフの運用で、次の 3 点が分かった。

  • 根は子の「通った」という報告を根拠にせず、受け入れコマンドを自分で流してから統合した。
  • 子のサンドボックスではポートを開けず e2e を流せないので、e2e はスケジューラと根が流した。
  • 3 往復で直らなかった作業は、同じ子に直させ続けず、別のモデルに引き継いだ。

スケジューラとサンドボックス

複数ステップの作業はタスクグラフとして tasks.yaml に書き、スケジューラが worktree ごとに子を起こす。 子は Claude Code の native サンドボックスの中で動き、ポートを開けない。 そのため子は e2e を流せない。

e2e を含む受け入れコマンドはスケジューラがレビューの前に流す。 通ったものだけがレビューに回る。 レビュアーは e2e の未実行を理由に差し戻さない。 git log の「検証前スナップショット」は、スケジューラが受け入れ検証の直前に残したコミットである。

自律の規則

開発者の不在中は /goal で各作業の流れを進めた。 判定役はファイルを読まずコマンドも実行しない。 だから条件は「どのコマンドが exit 0 になればよいか」の形で書く。 ゴールには必ずターン数の上限を付け、止まったら残課題を作業記録に書かせた。

/goal docs/roadmap.md の M1 を完了する。
証明: `pnpm typecheck && pnpm test && pnpm guard` が exit 0 で、
`pnpm test:e2e -- --grep <シナリオid>` でそのシナリオのリプレイが最後まで通ること。
制約: scenarios/ を変更しない。テストを削除・skip しない。
各ターンの作業内容を docs/progress.md に追記する。
40 ターンで停止し、残課題を docs/progress.md に書く。

見た目の良さと判断の妥当性はゴールにしない。 判定役は画面を見られず、現場の感覚は開発者にしか分からないからである。

4. 記録と再開

作業記録

docs/progress.md は各ターンの終わりに追記する。 書式は「やったこと、確認結果、残課題、開発者に確認したいこと」の 4 項目である。 新しい記録を上に置き、セッションをまたいでも最初の数行で現在地が分かる。

「開発者に確認したいこと」はこの開発の要になった。 エージェントは仮の値や仮定を置いて先へ進み、ここに問いを残す。 開発者は夜にまとめて答え、翌朝のゴールに反映する。 徒歩の上限、確信度の閾値、結末のカードで比べる相手は、この経路で決まった。

残タスク一覧

docs/remaining-tasks.md は提出までの残りを 1 枚にまとめる。 機能、文面、データと検証、デモと提出、開発者にしかできないこと、片付けの 6 区分である。 途中の作業はブランチ名と残りの手順を表に残し、別のセッションが引き継げる。

作業前に読む文書

CLAUDE.md は読むべき文書の一覧と、絶対に守る制約を先頭に置く。 製品仕様、審査基準、構成、データの利用条件、画面設計、ロードマップを分けて書き、迷ったら文書を正とする規則にした。 文書と実装が食い違えば、文書の更新を提案させる。

6. うまくいかなかったことと直し方

作業記録の残課題から 3 つを選んだ。 いずれも機械の検証が見つけ、記録を経て直した。

負荷で落ちる e2e

負荷平均が 20 を超えると、リプレイの最初の判断が 30 秒に収まらず e2e が落ちた。 原因は、workers の既定値で Playwright と判断処理が資源を奪い合っていたことである。 workers を 2 に制限し、起動確認を /replay にして初回コンパイルを先に済ませた。 既存サーバーの再利用を禁じ、指定ポートが使用中なら失敗させる。

動いている途中の位置で避けた札

地図の「見合わせ」の札が「全体を見る」のボタンに重なる失敗が、負荷の中で 8 回に 2 回出た。 ボタンは下の余白が変わると 200ms かけて動く。 札はその途中の位置を避けていたので、動き終えると重なった。 動き終えたあとの位置で避けるよう直し、同じ負荷で 24 回流して 24 回通った。

地図と探索で違った歩ける駅

塚本から三ノ宮へ向かうと、鉄道の代替が出ず「タクシーに切り替えてください」になった。 地図は直線距離から 15 分以内の駅を集め、探索は乗換の辺だけを歩く道にしていた。 塚本は辺が 0 本で、探索には歩ける駅が無かった。 駅の選び方を packages/geo の 1 つの関数にまとめ、地図と探索の両方が呼ぶようにした。

共通する教訓は、同じ事実を 2 か所で計算しないことである。 リプレイの結末の spec が独自に持っていた計算も、同じ理由で core の関数に寄せた。

作業の全体像

main で書く→ pnpm validate→ guard:approve→ コミット→ develop へ取り込み→ e2e で確認

knowledge/ と scenarios/ は開発者本人だけが書きます。

エージェントはこの 2 つを読むだけで、フックが書き込みを止めます。

pnpm guard は承認記録と照合し、無断の変更を見つけます。

そのため書く作業と承認は、必ず main ブランチで行います。

知見の書き方

知見は 1 事象 1 ファイルで、knowledge/<id>.yaml に置きます。

雛形から作るには次のコマンドを使います。id とファイル名がそろいます。

ALLOW_PROTECTED_EDIT=1 pnpm knowledge:new signal_failure

良い書き方の例は packages/schema/test/fixtures/dev-content/knowledge/ にあります。

ただし中身は開発用のダミーで、所要時間に根拠はありません。

項目の意味

項目意味
id事象を表す英小文字の id です。ファイル名と同じにします。
name summary事象の名前と概要です。概要は復旧までの流れを 2〜3 文で書きます。
identification.phrases発表文に出る事象の言い回しです。文字列照合で事象を見分ける手がかりになります。
phases段階を時系列の順に並べます。並び順がそのまま進む順になります。
phases[].signalsその段階にいると分かる兆候です。外から見聞きできるものだけを書きます。
phases[].duration_minutesその段階の所要時間で、p50 と p80 を分で書きます。
phases[].exit_signals次の段階へ進んだと分かる兆候の id です。
phases[].guidanceその段階で利用者に何を示すかの方針です。判断の文の書きぶりに効きます。
after_resume運転再開から乗れる列車が来るまでの目安です。分岐点の計算に使います。
caveats判断を誤りやすい点や、長引く型を書きます。
external_factors気象を判断材料に使うかを決めます。true なら雨量と警報を引きます。

en の欄は省けます。英語の画面で使うので、書けるなら書きます。

所要時間 p50 と p80

p50 は中央値です。半分の事象がこの分数のうちに次へ進みます。

p80 は長引く場合の目安です。8 割の事象がこの分数に収まります。

p80 は p50 以上にします。同じ値なら幅の無い固定の時間になります。

アプリは 2 つの値から分布を当てはめ、残りの段階を足し合わせます。

そのため段階ごとの値が、再開見込みの幅をそのまま決めます。

値は利用者として観察できる経過から決めます。社内の基準値は使いません。

迷ったら p80 を広めに取ります。狭すぎると「待て」に偏ります。

兆候の定義

兆候は、利用者が見聞きできる情報で定義します。

observable_from情報源
announcement事業者の公式の運行情報です。
signage駅の掲示や表示器です。
station_broadcast駅や車内の放送です。
weather雨雲や警報の情報です。
train_movement止まった列車や動き出した列車など、目に見える列車の動きです。

description には、何が起きたら兆候とみなすかを 1 文で書きます。

example_phrases は自作の例文です。実在の発表文は転載しません。

例文は API キーが無いときの文字列照合にも使います。

典型的な言い回しを 2 つ以上書くと、照合が当たりやすくなります。

兆候の id は知見の中で一意にします。事象の略号を頭に付けると重なりません。

段階のつなぎ方

アプリは観測された兆候のうち、最も先の段階を現在の段階とみなします。

段階は並び順に 1 つずつ進むのが基本です。

exit_signals に後の段階の兆候を書くと、途中を飛ばす経路になります。

たとえば発生直後に再開見込みが出れば、現場対応を飛ばせます。

最後の段階の exit_signals は特別で、運転再開の合図になります。

ここには「運転を再開しました」のような兆候を置きます。

id は、いずれかの段階の signals に定義したものだけが書けます。

phases:
  - id: initial
    signals:
      - id: pa_occurred_announced
    exit_signals: [pa_onsite_work_announced, pa_resume_estimate_announced]
  - id: on_site_response
    signals:
      - id: pa_onsite_work_announced
    exit_signals: [pa_resume_estimate_announced]

社内情報を書かない原則

社内の規制値、規程、内部手順の数値は書きません。

知見は外から観察できる兆候と、利用者の目に映る経過で定義します。

リポジトリは公開されます。書いた内容は誰でも読めます。

  • 数値は、報道や利用者の体感で説明できる範囲に収めています。
  • 兆候は、発表文や掲示や放送から読み取れるものだけです。
  • 例文はすべて自作で、実在の発表文を写していません。
  • 特定の事故や日時を思い起こさせる書き方をしていません。

シナリオの書き方

シナリオはリプレイと振る舞いテストに使う架空の事例です。

知見を先に作り、その id を --event に渡して雛形から作ります。

ALLOW_PROTECTED_EDIT=1 pnpm scenario:new signal_failure_morning --event signal_failure

良い例は dev-content/scenarios/person_accident_last_train.yaml です。

利用者と区間

項目書き方
event_type知見の id を書きます。存在しない id は検証で止まります。
operator line事業者名と路線名です。路線データの名前に合わせます。
blocked_section止まっている区間の両端の駅名です。
start_time日付と時刻を T で区切り、時差まで書きます。例は "2026-11-05T22:10:00+09:00" です。
user.constraints.deadline終電や約束の時刻を "00:25" の形で書きます。無ければ null です。
user.languageja か en です。

timeline

利用者が見聞きした観測を、時刻の順に並べます。

offset_minutes は start_time からの経過分で、昇順にします。

kind は兆候と同じ 5 種類から選びます。

文面は典型的な言い回しを参考に自作します。

再開見込みの時刻を書くと、アプリはその時刻を読み取って使います。

見込みを延ばす発表を入れると、判断が切り替わる様子を見せられます。

expectations

期待する振る舞いを、要所に数か所だけ書きます。

点数ではなく、振る舞いが壊れていないかを見る回帰テストです。

項目意味
afterどの観測を入れた後の判断かを、timeline の id で示します。
actionwait、switch、hold のどれを期待するかです。
phase期待する段階の id です。知見の phases から選びます。
evidence_includes根拠に含まれるべき兆候の id です。
break_even_shown分岐点が表示されるべきかです。
noteなぜそう振る舞うべきかの説明です。必須です。

検査する項目は省けますが、どれか 1 つは必ず書きます。

確信の持てない点は書かず、外したら困る点だけを書きます。

weather

大雨のように気象を使う事象では、架空の観測値を書きます。

リプレイ中は、この値が気象庁の実測の代わりに使われます。

offset_minutes は重ならない昇順にし、10 分ごとに並べます。

weather:
  readings:
    - offset_minutes: 0
      rainfall_10min_mm: 6
      warnings: [大雨警報]
    - offset_minutes: 10
      rainfall_10min_mm: 9
      warnings: [大雨警報]

気象を使わない事象では weather ごと省きます。

ground_truth

架空の「実際にどうなったか」です。デモの最後の比較に使います。

resume_offset_minutes は開始から運転再開までの分です。

再開しない筋書きなら null にします。

notes には、待った人と切り替えた人の結末を書きます。

作業の手順

1. main での執筆

git switch main
ALLOW_PROTECTED_EDIT=1 pnpm knowledge:new signal_failure
ALLOW_PROTECTED_EDIT=1 pnpm scenario:new signal_failure_morning --event signal_failure

どちらも既存のファイルは上書きしません。作ったあと次の手順を表示します。

あとは好みのエディタで TODO を埋めます。

2. 検証

別の端末で監視を始めると、保存のたびに検証し直します。

pnpm validate --watch

1 回だけ検証するときは pnpm validate を使います。

エラーの読み方は validate のエラーの読み方 にあります。

3. 承認

ALLOW_PROTECTED_EDIT=1 pnpm guard:approve
pnpm guard

承認は検証に通った内容だけを、端末での確認のうえ記録します。

記録は各ディレクトリの .approved.sha256 に書かれます。

pnpm guard がすべて合格になれば承認は完了です。

4. コミット

git add knowledge scenarios
git commit -m "知見: 信号故障と朝の通勤シナリオを追加"

YAML と承認記録を同じコミットに入れます。

5. develop への取り込み

git switch develop
git merge main
pnpm guard

main を経由していれば、develop の guard もブランチ差分で止まりません。

develop で直接書くと、main との差分として guard が失敗します。

6. e2e での確認

pnpm test:e2e

e2e は各シナリオの expectations から自動でテストを作ります。

e2e の読み込み元は、いまはダミー内容に固定されています。

場所は e2e/servers.ts の contentDir です。

本物の内容で回すには、この値を切り替える作業をエージェントに頼みます。

手元で本物の内容を見るなら、CONTENT_DIR を付けずに起動します。

JUDGE_MODE=deterministic pnpm dev

http://localhost:3000/replay を開き、書いたシナリオを流して確かめます。

ダミーから本物への切り替え

アプリは CONTENT_DIR で知見とシナリオの読み込み元を決めます。

未設定ならリポジトリの knowledge/ と scenarios/ を読みます。

場面切り替え方
手元の起動pnpm dev:demo はダミーを読みます。本物は pnpm dev で起動します。
検証pnpm validate:dev はダミーを、pnpm validate は本物を検証します。
Vercel環境変数の CONTENT_DIR を消して再デプロイします。
エージェントのコンテナデプロイの --set-env-vars から CONTENT_DIR を外します。

公開の手順は 公開手順書 にあります。

切り替えたら、起動ログの知見の件数が 0 でないことを確かめます。

知見が 1 本もそろわないうちは、公開環境ではダミーのまま残します。

claude モードの確認

実 API で claude モードを 1 回動かし、壊れていないかを確かめます。

export ANTHROPIC_API_KEY=<あなたのキー>
pnpm smoke:claude

キーが無ければ案内だけを出して終わります。費用はかかりません。

キーがあると、ダミーの主役シナリオの obs_1 と obs_3 を判断します。

あわせて架空の掲示の画像を作り、Haiku に読ませます。

確認合格の条件
イベント列のスキーマ届いた判断イベントがすべてスキーマに合います。
判断まで到達judgment_ready が届き、error がありません。
フォールバック無し解釈も判断も、決定論モードに切り替わっていません。
見出しと理由の長さ見出しと理由が設定の上限に収まっています。
画像の読み取り事象種別と再開見込みの時刻を画像から読めています。

2 つ目の表には、呼び出しごとの所要時間とトークン数が出ます。

キャッシュ読込が 0 のままなら、プロンプトキャッシュが効いていません。

NG が 1 件でもあれば終了コードが 1 になります。

失敗の原因は「API 呼び出しの失敗」と「警告」の欄に出ます。

掲示の画像は英大文字で描きます。日本語の字形を持たないためです。

このコマンドは pnpm test に含めません。実 API を呼ぶからです。

デモの録画

pnpm --filter e2e exec playwright install chromium
pnpm --filter e2e record

スマートフォンの縦画面でリプレイを自動操作し、録画します。

動画は e2e/recordings/ に出ます。git では管理しません。

録るシナリオは RECORD_SCENARIO で指定できます。

指定が無ければ、「切り替える」を期待する最初のシナリオを録ります。

再生の速さは RECORD_SPEED で変えられ、既定は 2 倍です。

RECORD_SCENARIO=person_accident_last_train RECORD_SPEED=1 pnpm --filter e2e record

録画も e2e と同じく、いまはダミー内容を読みます。

validate のエラーの読み方

エラーは 1 件ごとに 3 行で出ます。ファイル名と行番号の順に並びます。

エラー: 3 件
  - knowledge/signal_failure.yaml:37: phases.0.duration_minutes.p50: 無効な入力: 数値が期待されましたが、nullが入力されました
      説明: 「段階 1 › 所要時間 › 中央値 p50」が空です
      直し方: 所要時間の中央値を分で書いてください。例: p50: 15
  - knowledge/signal_failure.yaml:109: phases.3.duration_minutes.p50: 無効な入力: 数値が期待されましたが、nullが入力されました
      説明: 「段階 4 › 所要時間 › 中央値 p50」が空です
      直し方: 所要時間の中央値を分で書いてください。例: p50: 15
  - scenarios/signal_failure_morning.yaml:14: start_time: 無効なISO日時
      説明: 「開始時刻」が日時の形式ではありません
      直し方: 日付と時刻を T で区切り、時差まで書いてください。例: "2026-11-05T22:40:00+09:00"
ファイルごとの件数:
  knowledge/signal_failure.yaml: 2 件
  scenarios/signal_failure_morning.yaml: 1 件
行読み方
1 行目ファイル名、行番号、元のメッセージです。エディタで行番号へ飛びます。
説明どの項目に何が起きたかを日本語で示します。段階や観測は 1 から数えます。
直し方書くべき値や形の短い例です。

エラーが複数のファイルにあると、最後にファイルごとの件数が出ます。

雛形から作った直後は、TODO の数だけエラーが出ます。上から順に埋めます。

id の参照や並び順の検査は、書式の検査に通ったファイルだけに行います。

そのため書式を直すと、新しいエラーが出ることがあります。

知見を先に直すと、シナリオ側の参照のエラーも正しく出ます。

よくある誤り

誤り直し方
p50 や p80 が null のまま分を整数で書きます。例は { p50: 15, p80: 30 } です。
p80 が p50 より小さいp80 は長引く場合の目安なので、p50 以上にします。
exit_signals の id が未定義いずれかの段階の signals に同じ id の兆候を置きます。
知見の id とファイル名が違うどちらかに合わせます。knowledge:new で作れば最初からそろいます。
start_time の形が違う日付と時刻を T で区切り、+09:00 まで書きます。
deadline に日付まで書いた時と分だけを "23:45" の形で書きます。
timeline が時刻順でないoffset_minutes の小さい順に並べ替えます。
expectations の phase が別の知見の idevent_type に書いた知見の phases から選びます。
拡張子が .yml読み込まれないので、.yaml に変えます。
インデントがずれた空白 2 つ単位にそろえます。タブは使いません。
develop で直接書いたmain に移して承認し直します。guard のブランチ差分で失敗します。
